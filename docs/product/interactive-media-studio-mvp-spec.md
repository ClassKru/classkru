> สถานะ: ข้อเสนอ MVP เดิมแบบ template/SQL เก็บไว้เป็นประวัติ ต่อมาผู้ใช้เลือกสร้างสื่ออิสระและไฟล์ JSON ใน Supabase Storage โดยไม่เพิ่มตาราง media SQL; สิ่งที่ทำจริงดู [คู่มือติดตั้ง](interactive-media-studio-setup.md) ไม่ได้เริ่มจาก matching template ตามข้อเสนอเดิมด้านล่าง
>
> เอกสารต้นทาง: [Interactive Media Studio](interactive-media-studio.md)
>
> ความปลอดภัยสำหรับ custom web artifact: [Interactive Media Studio — Security](interactive-media-studio-security.md)
>

## 1. ข้อสรุปสำหรับ MVP

MVP ไม่ควรเริ่มจาก “ให้ AI สร้างเกม” แต่เริ่มจากวงจรที่ครูไว้ใจได้:

`brief สั้น → เลือก/แนบแหล่งข้อมูล → เลือกกิจกรรม → ปรับแผน → preview → ครูเผยแพร่`

ข้อเสนอสำหรับรอบแรกคือ pilot ระดับ ม.1–ม.3 เพราะ ClassKru มีคลังตัวชี้วัดระดับนี้อยู่แล้ว และใช้ template **จับคู่** เป็นสื่อโต้ตอบชนิดแรก ก่อนขยายไปยังลากวาง เรียงลำดับ ติดป้ายภาพ และ quiz

| เรื่อง | รอบแรก | ยังไม่ทำใน MVP แรก |
|---|---|---|
| วิธีใช้ | ครูนำบนจอฉาย หรือให้นักเรียนลองบนมือถือเป็นรายคน | เกมที่นักเรียนหลายคนส่งคำตอบสดพร้อมกัน |
| เนื้อหาจาก AI | สร้างและแก้ `activity definition` ที่ตรวจ schema ได้ | สร้าง HTML/JavaScript/CSS อิสระ |
| แหล่งอ้างอิง | ตัวชี้วัดที่ครูเลือก + ข้อความ/ไฟล์ที่ครูให้ | อ้างอิงจากเว็บแบบอัตโนมัติโดยยังไม่มีกระบวนการคัดเลือก |
| ผลงานที่เผยแพร่ | ลิงก์อ่านอย่างเดียวของสื่อรุ่นหนึ่ง | ตลาดแลกเปลี่ยนสื่อระหว่างครู |
| การเก็บผลนักเรียน | ไม่เก็บรายบุคคลใน template แรก | คะแนนหรือโปรไฟล์นักเรียนจากการเล่น |

การตัดสินใจนี้รักษาหลักของ ClassKru: ครูเปิดใช้ระหว่างสอนและเข้าใจได้เอง โดยไม่สร้างระบบ AI หรือระบบเก็บข้อมูลนักเรียนที่ใหญ่เกินกว่าคุณค่ารอบแรก

## 2. ประสบการณ์ของครู

### 2.1 จุดเริ่มต้น

ครูเปิดเมนู “สร้างสื่อ” จากคาบในหน้าวันนี้ หรือจากรายวิชา/ห้องที่เลือกอยู่แล้ว ระบบกรอกบริบทที่มีอยู่ให้ เช่น วิชา ระดับชั้น ห้องเรียน และตัวชี้วัดที่ครูเคยเลือก แต่ไม่ดึงรายชื่อนักเรียนเข้า prompt

หน้าสร้างสื่อมีสองคอลัมน์ตามเอกสารต้นทาง:

- **แผนสื่อ** ทางซ้าย: เป้าหมาย, เวลา, รูปแบบ, อุปกรณ์, Source Pack, โครงกิจกรรม, สมมติฐาน และสถานะตรวจงาน
- **ผู้ช่วยออกแบบ** ทางขวา: สรุปสิ่งที่เข้าใจ, เสนอทางเลือก 3 ทาง, และถามคำถามที่มีผลต่อแบบสื่อครั้งละหนึ่งเรื่อง

ทุกครั้งที่ AI เสนอการเปลี่ยนแปลง ระบบแสดงเป็น “ข้อเสนอที่จะอัปเดตแผน” ไม่แก้แผนเงียบ ๆ ครูเลือก **รับ**, **แก้เอง**, หรือ **ข้าม** ได้

### 2.2 ลำดับหน้าจอ

1. **เริ่มต้น** — ครูพิมพ์เป้าหมายหนึ่งประโยค หรือเริ่มจากตัวชี้วัด/คาบที่มีอยู่
2. **ตั้งต้นแผน** — AI สรุปบริบทและแสดงสมมติฐานที่ยังไม่ยืนยัน เช่น เวลา 50 นาทีหรือใช้จอฉาย
3. **เลือกแนวกิจกรรม** — แสดง 3 ทางเลือกที่ใช้ template ได้จริง พร้อมเวลา อุปกรณ์ และเหตุผล
4. **กำหนด Source Pack** — เลือกตัวชี้วัด, แนบเนื้อหา, หรือเดินหน้าต่อโดยระบุว่ายังไม่มีแหล่งยืนยัน
5. **ประกอบสื่อ** — ครูแก้รายการจับคู่ คำสั่ง เฉลย feedback และภาพประกอบใน form ที่ตรงกับ template
6. **ตรวจและลองใช้** — แสดง checklist และ preview สลับ `หน้าชั้น` / `มือถือ` ก่อนสร้างรุ่นเผยแพร่
7. **เผยแพร่** — ครูยืนยันว่าได้ตรวจข้อเท็จจริงและส่งออกลิงก์ของรุ่นนั้น

คำถามที่ครูยังไม่ตอบต้องแสดงเป็น chip “ใช้สมมติฐาน: …” ในแผนเสมอ เพื่อป้องกันงานที่ดูเหมือนพร้อมใช้ทั้งที่ตั้งอยู่บนข้อเดา

## 3. ขอบเขตความรับผิดชอบของระบบ

ระบบแบ่งเป็นสี่ชั้นที่แยกจากกันชัดเจน

```text
Brief + Source Pack
        ↓
Planner (สนทนา / ข้อเสนอ patch ที่อธิบายได้)
        ↓
Project + Version (ข้อมูลมีโครงสร้างและตรวจได้)
        ↓
Template Runtime (renderer ที่ผ่านการทดสอบ) → Preview / Stage / Link เผยแพร่
```

### 3.1 Planner

Planner รับเฉพาะบริบทที่ครูอนุญาตและคืนข้อมูลตาม schema ต่อไปนี้:

- `summary` — สิ่งที่เข้าใจจาก brief
- `assumptions[]` — ค่าเริ่มต้นที่ยังไม่ยืนยัน พร้อมเหตุผลและผลกระทบ
- `questions[]` — คำถามสำคัญที่สุดได้ไม่เกินหนึ่งข้อในแต่ละรอบ
- `activityOptions[]` — 3 ทางเลือกที่อ้างอิง template, เวลา, อุปกรณ์ และเหตุผล
- `proposedPatch` — การเปลี่ยนแปลงเป็น field ที่จำกัดไว้ของแผนหรือ activity definition
- `reviewFlags[]` — ข้อเท็จจริงที่ไม่มีแหล่งอ้างอิง, ข้อขัดกัน หรือจุดที่ครูต้องตรวจ

Planner ไม่มีสิทธิ์เขียนข้อมูลโครงการโดยตรง และไม่มีสิทธิ์สร้าง URL, แหล่งอ้างอิง หรือโค้ดที่ไม่มีอยู่จริง

### 3.2 Project และ Version

โปรเจกต์คือพื้นที่ทำงานที่แก้ไขได้ ส่วนรุ่นคือ snapshot ที่เผยแพร่หรือย้อนกลับได้ รุ่นที่เผยแพร่ต้องไม่เปลี่ยนเมื่อครูกลับไปแก้ draft

| วัตถุ | หน้าที่ | ข้อมูลสำคัญ |
|---|---|---|
| `media_projects` | เจ้าของและบริบทของงาน | `teacher_id`, `classroom_id?`, ชื่อ, สถานะ, draft รุ่นปัจจุบัน |
| `media_versions` | snapshot ที่ตรวจ/preview/เผยแพร่ | `project_id`, ลำดับ, `activity_definition`, plan, quality report, สถานะ |
| `media_sources` | สิ่งที่ครูเลือกให้เป็น Source Pack | ชนิด, ชื่อ, สิทธิ์การใช้, เนื้อหา/ที่เก็บไฟล์, สถานะประมวลผล |
| `media_source_segments` | ส่วนข้อความที่อ้างกลับได้ | `source_id`, ข้อความย่อย, ตำแหน่งต้นทาง, checksum |
| `media_version_citations` | ความสัมพันธ์ของเนื้อหาในสื่อกับแหล่ง | `version_id`, `activity_node_id`, `source_segment_id`, ประเภทการอ้าง |
| `media_reviews` | การยืนยันของครูและผลตรวจ | `version_id`, checklist, flags, ผู้ตรวจ, เวลา |

ใช้ `teacher_id = auth.uid()` และ RLS แบบเจ้าของงานเป็นค่าเริ่มต้น ไม่มีสิทธิ์อ่าน Source Pack หรือ draft ของครูคนอื่นจากลิงก์เผยแพร่

### 3.3 Activity Definition

ทุก template รับข้อมูลหนึ่งก้อนที่มี version ของ schema ชัดเจน ตัวอย่างแนวคิดสำหรับจับคู่:

```json
{
  "schemaVersion": 1,
  "template": "matching",
  "title": "จับคู่ส่วนประกอบของวงจรไฟฟ้า",
  "instructions": "ลากชื่ออุปกรณ์ไปจับคู่กับหน้าที่",
  "items": [
    { "id": "battery", "prompt": "แบตเตอรี่", "matchId": "source", "feedback": "เป็นแหล่งพลังงานไฟฟ้า" }
  ],
  "answers": [{ "id": "source", "label": "แหล่งพลังงาน" }],
  "completion": { "showAnswer": true, "retryIncorrect": true },
  "accessibility": { "colorIndependent": true, "keyboardEnabled": true }
}
```

ข้อมูลประกอบด้วยข้อความ, asset ที่ระบบอนุญาต, id และค่าที่ schema รับเท่านั้น ไม่มี HTML ดิบ, event handler, URL ที่ไม่ผ่าน validation หรือ JavaScript จาก AI

### 3.4 Template Runtime

Template runtime คือชุด renderer ที่เขียนและทดสอบโดยทีม ClassKru และทำหน้าที่:

- validate `activity_definition` ก่อน render
- แสดงการทำงานแบบลากวางและทางเลือกกดเลือก/คีย์บอร์ดที่ให้ผลเทียบเท่ากัน
- ให้ feedback จาก data ที่ครูตรวจแล้ว
- เก็บเพียง state ในหน้า preview สำหรับ MVP แรก
- ส่ง telemetry ที่ไม่ระบุตัวตนได้เฉพาะเมื่อครูอนุญาตในอนาคต

Template registry ระบุ `template`, `schemaVersion`, capability (ใช้ projector ได้, ใช้มือถือได้, ต้องมีภาพหรือไม่) และชุด test fixture ของ template นั้น การเพิ่ม template ใหม่จึงเป็นงานวิศวกรรมและ QA ไม่ใช่ผลลัพธ์จากโมเดลภาษา

## 4. Source Pack และการตรวจความน่าเชื่อถือ

Source Pack มีสถานะต่อ item เพื่อให้ครูรู้ว่าสื่ออาศัยข้อมูลใด:

| สถานะ | ความหมายบนหน้าจอ |
|---|---|
| `selected` | ครูเลือกให้ใช้เป็นบริบท |
| `cited` | มี node ในสื่อเชื่อมกลับถึงข้อความต้นทาง |
| `insufficient` | ต้นทางไม่พอสำหรับยืนยันข้อความ/เฉลย |
| `conflict` | มีข้อความในแหล่งต่างกัน |
| `teacher-review` | เป็นข้อเสนอจาก AI ที่ครูยังไม่ยืนยัน |

กติกาที่ต้องบังคับ:

1. AI ใช้ได้เฉพาะ source segment ที่ส่งให้หรือความรู้ทั่วไปที่ติดป้าย `teacher-review`
2. Citation ต้องเก็บ `source_segment_id` และตำแหน่งในต้นทาง ไม่ใช้ชื่อแหล่งที่โมเดลแต่งขึ้น
3. ถ้า Source Pack ว่าง สื่อยังสร้าง draft ได้ แต่เฉลยและข้อความเชิงข้อเท็จจริงต้องมี review flag
4. ข้อความจากไฟล์ที่ครูอัปโหลดต้องตรวจสิทธิ์การใช้งานก่อนสร้างลิงก์หรือแชร์ต่อ

ใน MVP ให้รองรับ Source Pack สองชนิดก่อน: ตัวชี้วัดจาก curriculum catalog และข้อความที่ครูวาง/แนบเอง ส่วนการอ่าน PDF, OCR และคลังอ้างอิงกลางเป็นงานที่เพิ่มหลังจากวงจรอ้างอิงพื้นฐานเสถียรแล้ว

## 5. Preview, Stage และการเข้าร่วมของนักเรียน

### 5.1 Preview ก่อนเผยแพร่

รุ่น draft ต้องผ่าน renderer เดียวกับสื่อที่เผยแพร่ และมี viewport อย่างน้อยสองค่า:

- **หน้าชั้น:** 16:9, 1280×720 พร้อมตัวอักษรและพื้นที่แตะ/คลิกที่มองเห็นจากท้ายห้อง
- **มือถือ:** 390×844, การแตะและคีย์บอร์ดทำงานได้โดยไม่ต้องลากอย่างเดียว

ผู้ตรวจสามารถเลือก “เริ่มใหม่”, “ดูเฉลย”, “จำลองคำตอบผิด” และดูรายการ node ที่มาจาก Source Pack ได้จาก preview โดยไม่แก้ข้อมูลผู้เผยแพร่

### 5.2 การเชื่อมกับ Stage ปัจจุบัน

`stage.html` ปัจจุบันรับ markup ผ่าน BroadcastChannel สำหรับ same-origin เท่านั้น. Runtime ใหม่ควรส่ง **serialized activity definition ที่ผ่าน validation** และ event ของ stage แทน `html`/`style` ที่ได้จาก AI. Stage adapter แปลง definition เป็น DOM ด้วย template runtime ของตัวเอง จึงไม่เปิดช่องให้ definition ที่บันทึกไว้ฉีด markup ได้

### 5.3 การเข้าร่วมด้วย QR

`join-activity` ปัจจุบันออกแบบสำหรับคำถามเดี่ยว (`short`, `choice`, `scale`) ต่อหนึ่ง session. ไม่ควรนำตาราง `join_activity_*` มาใช้เก็บ state ของ template โดยตรง เพราะรูปแบบ activity และการย้อนกลับรุ่นต่างกัน

เมื่อ template runtime เสถียรแล้วจึงเพิ่มชั้น `media_runs` และ `media_run_events` ที่อ้าง `media_version_id` สำหรับ QR join โดยเฉพาะ เริ่มจาก event ที่ไม่ระบุตัวบุคคล เช่น จำนวนผู้เข้าร่วม/ความคืบหน้ารวม ก่อนตัดสินใจเก็บคำตอบรายบุคคลตามนโยบายความเป็นส่วนตัว

## 6. สถานะ, สิทธิ์ และจุดที่ครูต้องยืนยัน

```text
draft → ready_for_preview → needs_teacher_review → ready_to_publish → published → archived
                     ↘ needs_revision ↗
```

- AI สร้างได้เพียง `draft` และเปลี่ยนเป็น `ready_for_preview` ได้เมื่อ schema valid
- checker ตั้ง `needs_teacher_review` เมื่อมี flags แต่ไม่มีสิทธิ์ลบ flag เอง
- ครูเจ้าของงานเท่านั้นที่ยืนยัน review และสั่ง `publish`
- การเผยแพร่สร้าง public token ที่ชี้ไปยัง **version เดียว**; แก้ไขครั้งถัดไปต้องสร้าง version ใหม่
- ครูยกเลิก public token หรือ archive รุ่นได้ตลอดเวลา

ก่อน `ready_to_publish` ระบบต้องบังคับให้ครูเห็นรายการต่อไปนี้: เป้าหมาย, เวลา, เฉลย/feedback, แหล่งอ้างอิงหรือข้อเสนอที่ยังไม่ยืนยัน, และผล preview ทั้งสองขนาดจอ

## 7. Quality Gate ที่อธิบายได้

Quality report ไม่ใช้คะแนนรวม แต่สร้างรายการตรวจผ่าน/ต้องแก้ พร้อม link ไปยัง node ที่เกี่ยวข้อง:

1. **เป้าหมาย:** ทุกกิจกรรมมี learning objective อย่างน้อยหนึ่งข้อ
2. **ความครบของเกม:** items, เฉลย, feedback ที่ถูก และวิธีตอบผิดครบตาม schema
3. **เวลา:** จำนวน items และรูปแบบกิจกรรมสอดคล้องกับเวลาที่ครูระบุ
4. **แหล่งอ้างอิง:** ข้อเท็จจริงและเฉลยมี citation หรือ `teacher-review` ชัดเจน
5. **การเข้าถึง:** ไม่สื่อความหมายด้วยสีอย่างเดียว, focus/keyboard ใช้ได้, ข้อความไม่ล้นบนมือถือ
6. **ความปลอดภัย:** ไม่มี HTML ดิบหรือ asset URL ที่ไม่ผ่าน allowlist
7. **ความเข้ากันได้:** fixture ของ template ผ่านใน viewport หน้าชั้นและมือถือ

ข้อใดเป็นคำแนะนำได้ไม่ควร block การเผยแพร่ แต่ข้อ 2, 4 และ 6 เป็น blocker จนกว่าครูจะแก้หรือยืนยัน review ตามกติกาที่กำหนด

## 8. ลำดับการพัฒนาเมื่อได้รับอนุมัติ

### Milestone 0 — Contract ก่อน UI

- กำหนด JSON schema ของ `matching/v1`, ตัวอย่าง valid/invalid และ validator
- ทำ fixture สำหรับ projector, มือถือ, การตอบถูก, ตอบผิด, และคีย์บอร์ด
- ยืนยัน policy ของ Source Pack, data retention และสิทธิ์การเผยแพร่

### Milestone 1 — Studio ที่ยังไม่มี AI จริง

- หน้า project/draft/version, Source Pack จากตัวชี้วัดและข้อความครู
- form สร้างสื่อจับคู่ด้วยมือ, preview, quality report และรุ่นเผยแพร่แบบ read-only
- RLS และ migration ของ media objects พร้อม test การแยกข้อมูลครู

### Milestone 2 — Planner ที่มี guardrail

- chat ที่คืน structured proposal patch เท่านั้น
- แสดง assumptions, ตัวเลือกกิจกรรม และ review flags
- ทุก patch ต้องผ่าน schema และรอครูกดรับก่อนเขียน draft

### Milestone 3 — เชื่อมจังหวะการสอน

- เปิด media version จากคาบในหน้าวันนี้และ Stage adapter
- เพิ่ม template เรียงลำดับหรือ drag-and-drop เพียงหนึ่งแบบตามผล pilot
- ทดสอบกับครูจริงเรื่องเวลาตั้งสื่อ, ความเข้าใจคำสั่ง และความเสถียรหน้าชั้น

### Milestone 4 — QR run (หลัง runtime ผ่าน pilot)

- ออกแบบตาราง run แยกจาก join activity เดิม
- เริ่มจากข้อมูลรวมและการยินยอมที่ชัดเจนก่อนเก็บคำตอบรายบุคคล

## 9. เกณฑ์ว่าพร้อมเริ่มพัฒนา

ก่อนเปิด branch หรือสร้าง migration ต้องได้คำตอบและบันทึกการตัดสินใจอย่างน้อย:

- ยืนยัน pilot: ม.1–ม.3 + template จับคู่ หรือระบุกลุ่มเป้าหมาย/แม่แบบอื่น
- ยืนยันว่า draft แบบไม่มี Source Pack เผยแพร่ได้หรือไม่ และครูต้องยืนยันอะไร
- กำหนดนโยบายไฟล์ที่ครูแนบ, อายุการเก็บ และสิทธิ์ใช้ซ้ำ
- ตัดสินใจว่าลิงก์เผยแพร่เปิดสาธารณะ, ต้องใช้รหัส, หรือจำกัดเฉพาะนักเรียนในห้อง
- ระบุว่า offline รองรับระดับใด: preview ที่ดาวน์โหลดแล้ว, ทั้ง template, หรือไม่รองรับในรอบแรก
- ระบุเจ้าของความถูกต้องของเนื้อหาและช่องทางรับรายงานข้อผิดพลาด

เมื่อคำตอบครบ จึงแปลง Milestone 0 เป็น issue ที่มี acceptance criteria ได้โดยไม่ต้องเดาเรื่องสิทธิ์, ความเป็นส่วนตัว หรือความน่าเชื่อถือภายหลัง
